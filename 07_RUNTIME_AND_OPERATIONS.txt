# 羊年年会现场游戏平台 运行协议与现场操作 V2.2 交接修订

编制日期：2026-10-26。交付包V2.2；候选规则版本仍为onsite-v2.1-candidate。
V2.2补场阶段歧义修正：未封榜PLAYING/DRAINING均可创建和使用指定原槽单次授权；普通预约不占授权保留槽。规则JSON及数学不变，原51案例ID保留，新增M01/M02后共53项。
本文件与01产品、02规则、03技术及同版JSON共同构成实施规范；它固定运行时、后端和现场异常处理，不另设游戏计分公式。06号文档负责真人难度与得分分布门槛。

## 1. 范围与不可变约束

1. 一个event内每人固定三个槽，编号1、2、3；一个槽有多条尝试历史，但只有一条当前绑定尝试及至多一个有效贡献。已用机会不按天重置。
2. 每次start成功占槽，正式逻辑seed按游戏固定为stack=1、runner=1、herd=47；runner使用固定赛道表。session_id及随机session_nonce区分局次。控制凭证另行生成；seed和nonce不用于证明真人操作。
3. 每个合法自然终局且存在有效操作并通过核验，获得20参与分及0..80表现分；单局≤100、三槽≤300。零操作、主动放弃、无效、未按时交齐均0分，原因分别保存。
4. 所有正式局绑定同一已发布规则快照和模拟核版本。规则冻结发生在挑战开放前；榜单冻结发生在DRAINING结束、开放兑换时。规则冻结不妨碍按相同规则进行获准补场；榜单冻结后禁止补场。
5. 账户、余额、库存、任务和审计持久化于PostgreSQL。主线程内存只承担运行协调，不能充当唯一的成绩或订单存储。
6. 首版仅一个Fastify API进程实例，配有限worker_threads核分池。不开cluster，不静默增加API副本。多API须先增加共享受理屏障并重做本文件竞争测试；不能仅加负载均衡或粘性会话。

## 2. 时间与时钟

### 2.1 唯一时轴

created_at：start事务获得所需锁并作出成功准入决定时采样的服务端时间，随局记录提交。它不是请求刚进入网络的时刻；事务回滚则不存在有效预约。

play_started_at = created_at + 3000ms
play_ends_at = play_started_at + 45000ms
submit_deadline = play_started_at + 60000ms

以上字段创建后不可被重试、恢复、暂停、补传或客户端校时改写。提前自然终局也不另计算一个“结束后15秒”的提交截止。

| 操作 | 服务端边界 |
|---|---|
| 普通预约准入 | created_at < challenge_closes_at |
| 原槽补场准入 | created_at < makeup_grant.admission_deadline |
| 正式输入 | 对应逻辑tick1..1350，预约倒数期间不能输入 |
| 首次完整终局提交 | play_started_at <= received_at <= submit_deadline |
| 新兑换 | phase=REDEEMING且操作时刻 < claim_closes_at |
| 核销已有订单 | 核销事务校验时刻 < claim_closes_at |
| 到期取消未领取 | 当前时刻 >= claim_closes_at |

finish的等号与claim的不等号不能混用。claim按取得所需锁后、执行状态转换前重新采样的服务端时刻判断，不因HTTP请求较早抵达就预占领取资格。start也在取得锁后重查准入时间。

服务器业务时间由同一个受控API时源提供并持久化，使用UTC时间戳及毫秒精度；不混入客户端墙钟，也不在同一判断里混用有偏差的不同机器时源。部署时检查API/数据库主机时间与UTC偏差。

### 2.2 响应与客户端映射

start、GET event、GET session和幂等重试的每个响应都生成新的server_now；不可将旧响应里的server_now原样缓存。可同时返回server_received_at和server_sent_at，用于排除请求处理耗时；不缓存包含个人局次或时间快照的响应。

客户端在发送和接收时用单调时钟记录样本，优先采用低RTT样本估计服务端偏差。使用收发双时间戳时可扣除服务端处理时长；样本仅用于显示和调度。RTT中点仍有上下行不对称误差，不能宣称消除全部网络差异。

客户端显示实际剩余预约倒数。收到响应已过play_started_at时，从原初值按已过逻辑时间和合法日志补推进，不从接收时刻再运行45秒。重试已过submit_deadline时恢复原终态/超时结果，不重新开局。

运行中校时不倒退processed_tick，不给过去的tick追加玩家操作；不把手机Date.now变化变成可玩时长。纯模拟核只接收固定步和规范化输入。3秒缓冲减少一般链路损耗；确认系统故障影响的局按原槽故障流程处理，不无证据自动返机会。

### 2.3 未来输入校验

先要求received_at位于上述允许提交区间，再计算：

allowed_tick = min(1350, floor((received_at - play_started_at + 250) * 30 / 1000))

highest_input_tick和end_tick都不得大于allowed_tick。没有输入时highest_input_tick=0；end_tick仍须是1..1350。每条输入须满足1<=tick<=end_tick。250ms不能延长45秒模拟上限或60秒提交截止。

服务器从初始状态重放至首次合法终局，复算结束tick与原因；必须与提交的end_tick、end_reason一致。runner正常正式局只在1350tick以TIME_LIMIT结束，碰撞不提前结束，不存在生命值或LIFE_OUT。未形成自然终局却提前声明完成、在已结束后追加输入到日志、提前伪造1350tick都不能获分。模拟核对已结束状态保持不变，协议仍会拒绝超过首次终局的上传日志。

## 3. 身份 控制归属与幂等

### 3.1 角色和对象权限

| 角色 | 可以执行 | 不能执行 |
|---|---|---|
| PARTICIPANT | 查看本人的event、槽、局、订单；自己的预约、原控制端提交/放弃、兑换和未领取取消 | 改他人局/订单、控阶段、核销、改库存、作废或补槽 |
| REDEEMER | 在授权event查询领取必要信息、核销符合条件的订单、查询原核销结果 | 改阶段/库存/积分、补槽、全量名单导出 |
| ORGANIZER | 授权event的配置、阶段、复核、更正、原槽授权、库存、核销及导出 | 跳过阶段/截止/槽上限/审计，直接修改余额伪造结算 |

每个接口先确认服务端会话与权限，再确认对象event和owner。session_id、order_id、UID或公开二维码都不是授权凭证。管理功能不依靠隐藏按钮保护；跨event、跨参与者对象一律拒绝。

个人邀请码/二维码使用不可猜测随机凭据，服务端只存其哈希。手输短码另明确熵和尝试限制，不以连续工号、姓名或可穷举短编号作口令。尝试限制兼顾同场Wi-Fi多人，不只用很低的单IP阈值。登录错误不枚举名单。

登录请求在发出前保存login_nonce；同一次个人码与nonce的响应丢失可安全恢复同一绑定身份与会话，不创建另一份三槽额度。个人码用尽后，另一个nonce不能二次领身份。实现可用安全可恢复的会话签发方式，但不能保存明文个人码作为查询索引。

会话使用安全Cookie属性或等效安全凭证；写接口校验来源及必要的CSRF保护。账号恢复、人员资格取消或权限撤销应即时使旧会话和旧运行控制权失效。开发身份只在显式开发环境存在；生产不能自动载入测试名单/管理员。

### 3.2 原控制端

start请求带client_instance_id、client_version、simulator_version、rule_version、rules_hash、game_id、idempotency_key，以及需要时的makeup_grant_id。

客户端在发出start前用安全随机源生成并持久化至少128位controller_secret，随已认证start提交；服务端仅保存哈希并绑定auth_session_id、client_instance_id和controller_epoch。这样即使start响应丢失，原客户端仍持有控制凭证；重试不要求服务器从哈希反推出明文。

finish和abandon首次产生副作用时必须同时匹配当前认证会话、控制版本与controller_secret；已有业务的幂等查回只按已认证权限及对象归属返回当前状态，不恢复任何旧写入权。已撤销的认证会话仍被拒绝，新设备可用自己的有效会话通过GET查询本人结果。GET /me可让同一人其他设备看见“有一局进行中”，但不把运行凭证交给其他设备。控制凭证不能进入公开URL、榜单或普通访问日志。

正常刷新从本地恢复相同实例、凭证和完整输入。工作人员恢复身份时撤销旧会话、提高控制版本并审计；没有完整旧输入的新设备不能从初始空日志续跑原局。已封存的成绩可跨设备查询；未封存且无法恢复的局按实际原因放弃、超时或有证据的系统故障原槽补偿处理。

同浏览器多标签页用单实例协调提示防止误操作；服务端仍检查控制归属。该约束不宣称能够阻止用户主动复制凭据或所有合法脚本。

### 3.3 幂等

幂等唯一范围至少为(event_id, participant_id, operation, idempotency_key)。处理顺序固定为：认证及接口权限、原对象归属、规范化业务摘要、已有幂等记录；同键同参数返回原对象的当前状态，同键不同game_id、grant、gift或其他业务参数返回409 IDEMPOTENCY_CONFLICT。只有尚不存在的新副作用才检查当前准入阶段、资格、截止及可写状态；持业务锁后再次查幂等记录，避免并发请求重复执行。身份、余额、发分不能由客户端自报覆盖。

已有结果的查询不能因为活动暂停、进入DRAINING/CLOSED、领取截止已过或后来冻结资格而被当作新操作拒绝；认证撤销、越权或摘要冲突仍须拒绝。返回的是原对象现在的状态，可能为VOIDED、CANCELLED或CLAIMED，不把缓存的历史成功响应当作现在仍然有效的结果。

start、兑换、取消、核销和工作人员补偿均有独立业务键。finish以session_id和首次封存过程摘要唯一；首次规范化日志固定后不能用另一过程覆盖。重复请求不得重新执行副作用；server_now可更新，原局时轴和原成交价不能更新。

网络失败后重试使用原键；如果不确定是否成功，先查原对象。不能在每次HTTP重试时自动生成新键。凭证、邀请码和控制secret从日志中脱敏。

## 4. 输入采样 本地日志与恢复

### 4.1 规范化输入

初始状态tick=0，逻辑依次处理1..1350。输入结构为{tick,seq,type,value}。tick与seq须为JavaScript安全正整数；seq整局递增、允许缺号，tick随seq不倒退，同tick按seq升序。先识别相同seq重复：内容一致只执行一次，内容不同拒绝整份过程。去重后仍须满足顺序和每tick限制。

| 游戏 | type与value | 每tick上限 |
|---|---|---|
| stack | DROP，value省略或null，规范化为null | 1条 |
| runner | JUMP，value省略或null，规范化为null | 1条 |
| herd | DOG_MOVE，value={x,y}，每分量-1000..1000整数 | 1条方向 |
| herd | BARK，value省略或null，规范化为null | 另1条吠叫 |

未知type、非有限数、非法范围或客户端位置/已入圈列表等局内状态覆盖字段拒绝。DOM指针事件不是直接上传格式；实际逻辑使用的规范化输入才是日志。UI菜单、音量和返回点击不穿透成玩法输入。

离散输入在实际状态不合法时由模拟核忽略，不增加有效操作数。DOG_MOVE只作用于一个tick；该tick缺省为(0,0)，绝不继承上一tick。移动是否有效依实际位移，BARK是否有效依02的冷却和影响条件。

原始输入数组在去重前最多4096条，完整UTF-8 body最多262144字节。每tick条数在规范化去重后校验。不能利用无数重复输入绕过长度限制。

### 4.2 实时采样与松手

事件发生于玩法逻辑经过时间elapsedMs时，候选tick为floor(elapsedMs*30/1000)+1；不得把输入放入已处理tick。只向尚未处理的下一合法tick及其事件对应时刻排队，超过1350丢弃。预约期没有玩法输入。

前台持续按住方向时，客户端每个逻辑tick都采样该tick时刻的控制状态并记录DOG_MOVE，不能只在pointermove发生时记一条。控制状态变更保留发生时刻，以便低帧时准确补推进。

同tick多次方向采样在该tick真正模拟前合并为最后一条；模拟消费并记入日志的是同一个值。不能先用较早方向跑物理，上传时才改成另一条。DROP/JUMP同tick连点规范化为一次，不能产生第二次动作。

pointerup、pointercancel、lostpointercapture、键盘松开、窗口失焦与visibilitychange(hidden)立即清空当前控制状态；合并时保留清空结果。本tick实际没有非零方向可省略DOG_MOVE或记录(0,0)，两者模拟一致。切后台后不继续采样按住状态。

低帧率或暂时不渲染时，逻辑仍按应有tick推进。补赶历史tick只能消费该时刻已经发生且未被清空的控制状态及已排队动作，不能用恢复时的新手势回填过去tick。后台、失焦或确无历史输入的时段方向为零、动作为空。画面可跳过中间动画，不能跳过碰撞或延长时钟。

### 4.3 本地持久化

开始前确认本地持久化可用。保存start幂等键、控制secret、原局元数据和时间映射。过程中增量保存规范化日志、最后seq及处理到的tick；checkpoint标明对应规则版本和日志摘要，只用于加快端侧恢复。

终局生成一次规范化完整请求并持久化，之后所有补交复用相同内容。查询到服务器已封存时只轮询结果，不继续本地游戏或重组过程。

刷新后先读取缓存，再向服务端查询原局和新server_now。完整日志在同版模拟核中重放至缓存位置，再按当前服务器时轴补推进；缺失期间无输入。离线刷新无法获得可靠的新时轴时显示等待恢复，保持缓存，不开启一份新局；联网后仍受原截止限制。

日志前缀缺失、持久化不可恢复或需要的旧模拟版本不存在时，不能用空日志/客户端快照/分数冒充完整过程。内存中完整日志仍在时可正常完成并提交；只有不可恢复时才进入相应失败说明与申诉。普通本地数据清理不自动返槽，确认系统故障才审计补偿。

服务端从未接收的中途输入不能凭GET恢复出来。本版不需要高频逐操作上传。

## 5. 预约 准入与原槽补场

### 5.1 预约事务

1. 创建新预约前完成资源、版本和本地缓存预检，用户明确确认使用一次机会。服务器收到请求先认证、确认归属、比对摘要并查已有幂等业务；已存在则返回原对象的当前状态与新server_now，不再检查新预约阶段或截止。
2. 确认尚无旧业务才进入事件阶段关口，锁定participant并按稳定顺序锁定相关ticket和session。持锁后先再次查询幂等记录；如果另一并发请求已完成，返回同一原对象。
3. 仍不存在旧业务时，清理已过截止且没有准时受理占用的旧局，重查同人没有SCHEDULED/RUNNING/AWAITING_SUBMISSION局，且资格有效、入口开关允许。不能清理正在受理的正常完整提交。
4. 普通场要求PLAYING、榜单未冻结、created_at<challenge_closes_at；带grant的补场要求PLAYING或DRAINING、榜单未冻结、有效原槽授权、created_at<该授权admission_deadline。补场不再叠加普通challenge_closes_at限制，可跨普通截止在DRAINING使用。accepting_new_sessions=false时两种新预约均拒绝；打开开关不会改变阶段或扩大补场名单。
5. 普通场选服务器决定的普通可用槽，并跳过已被有效grant保留的槽；无其它普通可用槽则拒绝，不自动消费grant。补场只使用授权原槽。按game_id取冻结seed（stack=1、runner=1、herd=47），生成随机局ID/nonce，绑定规则与控制归属，建立3秒后的时轴；原子占槽并将补场授权标为已使用。
6. 提交成功后返回session_id、slot_no、game_id、seed、session_nonce、rule_version、rules_hash、simulator_version、client_version、controller_epoch、created_at、play_started_at、play_ends_at、submit_deadline、状态及新server_now。controller_secret已由原客户端持有，不返回给其他设备。

唯一约束保证每个participant至多一条未封存活动局、每个原槽只有一个当前绑定。时间到后的状态由服务端时间推导，周期任务只负责及时物化；不能依赖一个浏览器定时器才能从SCHEDULED进入RUNNING。

start成功后的主动取消/返回大厅属于ABANDONED，槽已消耗且0分。预约倒数也不例外。资源在start前加载失败或取消预检不占槽。

### 5.2 暂停与紧急中止

普通暂停仅令accepting_new_sessions=false；在途预约照原时间开赛，在途运行照原时钟完成、提交。暂停不会改challenge_closes_at。

紧急中止先关新入口，再按事件和原局记录选取受影响的SCHEDULED/RUNNING/AWAITING_SUBMISSION尝试，审计作废并为对应原槽创建单次grant，槽位保留给该授权。已准时封存且未受影响的正常成绩不自动作废。现场需要把某一已封存局列为故障时，必须明确选中并走有审计的作废流程。

系统中止与正常放弃的原因分开。普通挑战恢复只能在原允许PLAYING窗口内；系统故障grant可在未封榜PLAYING或DRAINING使用，按授权自身截止，不向所有人增加普通机会。榜单冻结后不恢复挑战或发补场。

### 5.3 补场授权与作废

授权绑定event、participant、original_slot_no、admission_deadline、授权原因及操作者。只能在榜单未冻结的PLAYING/DRAINING创建和使用，且只能消费一次；重复请求返回同一授权/尝试，不新增槽。授权创建即保留原槽，普通start不可消费；取消或到期表示本次补偿已处置，不把该槽重新变成普通可用。补场仍使用同版规则与该款冻结seed，不保留旧分、不从历史取高分。

原槽替换在一笔短事务内先取得event阶段锁，再锁participant、ticket、旧session，确认当前绑定；若已有匹配局的可能有效首次提交正在受理，先返回RECEIPT_PENDING，待受理明确后再由工作人员处理。已经VERIFYING的局可在明确故障处置中作废，但须使对应任务失效。

替换事务将旧局标VOIDED并提高绑定/控制版本，已入账则追加唯一全额冲正，将同一槽保留给指定授权并创建grant。之后到达的旧finish或旧核分结果不能复活旧局。若提交和替换同时争用，按当前绑定与锁内状态线性化：先被持久受理的过程可被后续有审计的作废覆盖；已完成替换的旧局不得再受理。任何路径最多保留一个当前有效贡献。

## 6. 完整提交 受理屏障与超时

### 6.1 入口受理登记

首版在单API主进程维护inflight_finish登记表，至少记录request_id、路由session_id、完整body的received_at、classification和blocks_seal。普通HTTP请求跟踪数与封榜阻塞数分开；封榜只等待可能改变当前贡献的准时首次受理。

在读取到受大小限制的完整body的同步入口，采样received_at并登记为UNCLASSIFIED、blocks_seal=true；在第一个异步认证/数据库等待之前完成。登记不依赖先查数据库，也不等待封榜的主进程协调锁或event数据库锁。路由ID只是协调索引，后续仍验证真实owner和event。

分类可以异步取得证据，但分类未完成期间原阻塞标记始终保留。单主线程在一个同步步骤中原地更新分类和阻塞状态，禁止“先减计数→await认证/查库→再加计数”的漏窗：
- POTENTIAL_FIRST：当前event、当前绑定、尚无已持久化过程，received_at可能在允许区间；持续阻塞到受理持久化或明确失败。
- NON_BLOCKING：已有持久化过程的幂等查回/冲突请求，或已明确迟到、过早、无权、格式非法、已作废/放弃/替换，均不能产生新贡献；及时移出封榜阻塞，但普通请求跟踪可保留至响应完成。
- UNCLASSIFIED：尚未取得足够证据，尤其可能按时首次到达的body；保守继续阻塞，不能把“尚未识别”当成“无效”。
- DURABLE或FAILED：受理及任务已持久化，或事务已确定未提交且本次处理明确失败；移出入口阻塞，前者由数据库VERIFYING/任务状态继续阻止未完成封榜。

已明确重复、迟到或无权的请求不应长期占住封榜。封榜事务可用锁内的权威场次快照进一步确认某条登记不可能影响该event：例如所指局已持久封存、终态不可恢复、已非当前绑定，或received_at超过该不可变截止。没有足够事实排除的登记仍阻塞；不能只凭客户端字段过滤。

不能在返回202前只把body留在内存。数据库提交状态未知时保持保守阻塞并按session唯一键查询，不能盲目释放登记后用新键重做。API设置有限body读入、认证和数据库等待；请求异常在finally中清理普通跟踪，并留下明确分类/处置结果。未确定的数据库结果进入恢复处理，不伪称成功或通过清计数强行封榜。

### 6.2 受理事务

先验证认证、接口权限、对象归属和形成业务摘要所需的格式，不先执行首次提交的阶段、截止或可写资格检查；随后查已有首次封存摘要。同摘要只返回该局当前状态，不更新received_at、不重复创建任务；不同摘要返回409 PROCESS_ALREADY_SEALED。摘要基于规范化输入、结束信息及绑定版本；纯JSON空白差异不改变摘要。已有记录后来为VOIDED时返回VOIDED当前状态，不播放历史已到账响应。

尚无封存过程才进入首次受理：验证当前控制权、绑定版本、该局绑定的规则/构建、完整输入schema和时轴，按统一锁顺序读取participant、ticket、session，并在锁内再次检查是否已有封存。因并发请求先完成而已存在时，按同一摘要规则返回，不继续执行新副作用。

首次过程所指局若为VOIDED、ABANDONED、已替换或控制权失效，拒绝，不能因客户端声称早已完成而恢复。若received_at>submit_deadline，首次请求判超时；同一内容此前已经准时持久化时，截止后的重试只查回当前状态，不再过首次提交的时轴检查。

若完整body在期限内到达且仍是当前绑定，受理可以将临时TIMED_OUT纠正为VERIFYING，前提是它没有被放弃、作废或替换。数据库排队耗时不替代received_at。受理同时写入不可变过程摘要/日志、首次received_at和唯一pending任务，然后提交并返回202/已存在结果。

client_summary仅作诊断对比；服务器不信任其中分数、位置或状态，也不凭预测UI值发分。真正合法性与计分只来自受理日志的重放。

### 6.3 与超时 放弃 替换的竞争

超时任务只有在当前时刻严格超过submit_deadline、没有已封存过程、没有对应的准时POTENTIAL_FIRST或仍可能按时的UNCLASSIFIED登记时，才把未封存局改为TIMED_OUT。新start清理旧在途使用同一条件；不能绕过受理占用直接腾挪旧槽。已明确NON_BLOCKING的迟到/重复/无权请求不持续挡住超时处理。

原控制端abandon在取得所需锁后，若过程已封存或有同局可能有效的首次受理正在处理中，返回已提交/受理中状态，不把它改成放弃。否则通过条件更新转ABANDONED并记0分。与finish同时发生时，只允许一个结果；先成功持久化的终态/绑定约束后续操作。

补场替换按第5.3节；已有可能有效或尚不能排除有效的入口登记时，优先让受理得到确定结果。并发瞬间若替换已经完成，旧body即使早于原提交截止仍不能覆盖新绑定，因为工作人员已经明确作废了原尝试并恢复原槽机会。

### 6.4 封榜屏障

DRAINING→REDEEMING的主进程协调锁只串行化阶段命令，不拦截入口登记，也不被finish持久化/释放登记路径等待。随后取得数据库event排他锁，读取该event的权威场次、绑定和任务快照；在锁内检查：
1. 可能改变当前贡献的首次受理阻塞数为0，包括可能按时但尚未完成分类的UNCLASSIFIED；已明确幂等查询、迟到或无权的普通HTTP请求数可以不为0；
2. 没有SCHEDULED/RUNNING/AWAITING_SUBMISSION局；所有未提交局已过自己的submit_deadline并处理；
3. 没有VERIFYING、待恢复核分任务、未决REVIEW或未完成补偿；
4. 所有有效未用补场授权已使用、到期或经审计明确取消；
5. 规则发布/事件恢复检查通过；claim_closes_at已配置且大于当前时刻。

发现任何有效或尚不能排除有效的受理未完成，立即回滚并返回RECEIPT_PENDING及数量；绝不持event排他锁或阶段协调锁等待受理计数归零、finish取得锁或核分线程完成。这样，被event锁挡住的finish能在回滚后继续持久化，不形成“封榜等finish、finish等封榜”的循环。

阶段排他锁阻止新的普通/补场准入、新授权及其他成绩写入。所有场次快照已确认不存在尚可由未来新到达body产生贡献的局：未封存但可补交的局已过自己的deadline；其余已持久封存或不可恢复终态。已完整到达的潜在准时body必定已在同步入口登记，不能落在任何异步过滤空窗内。

完成数据库关口检查并准备阶段更新后，在发出COMMIT之前用同一主线程同步重扫登记表，并以锁内权威快照重新核算阻塞；中间不await分类工作。未分类且仍可能有效的一律计入。若不为0，回滚整个阶段事务；若为0，立即发出COMMIT，写入rank_frozen_at、rank_revision及REDEEMING，不在最终扫描和发出COMMIT之间另做异步等待。COMMIT等待期间新完整到达的body只可能是已超时、终态请求或已封存查回；其received_at不可能回到此前未登记的过去。无法证明这些前提时，不允许封榜。

入口登记只在单实例中有效。增加第二API会使一个实例看不到另一个实例的准时body，因此在完成共享屏障前禁止多API部署。

### 6.5 进程退出与恢复

正常停止先关新预约、停止新管理阶段变更，等待入口受理明确落库或明确失败；已持久核分由数据库租约恢复。不可在有未落库body时声称已经安全封榜。

异常进程重启会丢失尚未持久化的入口登记。对仍在PLAYING/DRAINING的受影响事件，启动时先暂停新预约并设置recovery_review_required；检查原局、客户端补传和任务租约，由主办方审计确认后解除。没有持久化接收证据、且重试已经超过截止的body不能伪称先前按时收到；保存事故信息，在榜单未冻结时按有证据的系统故障原槽补偿。未恢复检查通过不能封榜。

已经向客户端确认受理成功的记录必须在数据库中存在。数据库恢复与备份/迁移按现场部署步骤演练；本地演示不等于已完成生产恢复。

## 7. 数据库锁与核分任务

### 7.1 锁顺序

所有业务写路径采用同一部分顺序，只锁自己需要的对象：

event阶段关口 → participant → ticket（slot顺序）→ session（ID顺序）→ gift（ID顺序）→ redemption（ID顺序）→ replay_job

首次预约/提交/结算/订单副作用使用event共享阶段锁；阶段转换、封榜及冻结后榜单修订使用event排他锁。新start、下单和claim在取得所需锁后重新采样各自准入时刻并重查阶段。finish是明确例外：received_at永久使用完整body同步入口的采样值，拿到event锁、participant锁或session锁后都不得重采样它。已有业务的幂等查回不执行新副作用准入检查。不能先拿participant锁再回头等event锁。

取消/核销可先无锁查询订单的不可变owner和gift标识，再按上述顺序加锁并重读订单状态。订单owner、event、gift和成交价创建后不可修改。批量补偿稳定排序或每人短事务，不能A→B与B→A反向持锁。

租约领取是独立短事务，仅锁job行并立即提交；不在持job锁期间再等待participant，也不持业务事务跑CPU模拟。回写才按上述完整顺序锁定需要的行。

数据库检测到死锁或序列化回滚时，整事务回滚并有限重试同一业务键。超出重试上限返回可定位错误并保留原业务状态，不能生成新键或手工补一笔积分。

### 7.2 任务领取与旧结果隔离

job至少包括status、lease_token、lease_generation、lease_expires_at、attempt_count及error。领取pending或过期任务时原子更换token、递增generation。必要的续租也必须匹配当前token；最多有一个当前有效租约。

worker完成/失败回写须匹配当前job为运行中且token/generation一致，并重查session仍绑定原槽、未作废、已受理同一过程。过期线程结果只记诊断，不得改任务状态、局结果或余额。

成功结算在一个事务内落核验结果、奖励资格、表现分、唯一积分流水和job终态。失败分为过程违法和基础设施错误：前者按规则无效0分；后者有限重试后转REVIEW，不能冒充玩家作弊或自动发分。

工作线程池和数据库连接池均设有限并发。任务积压显示“核验中”，不提前显示已到账；可以开始另一个剩余槽，但同人不得同时有第二个未封存局。

## 8. 计分 榜单 冻结后更正

荣誉累计 = SUM(三个槽当前有效贡献)
可用余额 = SUM(该参与者全部有符号point_ledger)

流水类型至少有SESSION_CREDIT、SESSION_REVERSAL、REDEMPTION_DEBIT、REDEMPTION_REFUND。每笔都有唯一业务事件键及关联对象。冲正保存负向原获分，退款保存正向原成交价；不删除/覆盖原流水。

例：三槽73、40、65，无订单时累计和余额178；作废73后均为105，不是32。若此前扣了100分订单，则余额为5、累计105。取消该未领取订单后余额105，累计仍105。

正式榜只包含至少一个已核验并满足有效参与资格的槽的人员；其他显示待完成/待核验，不作为0分并列第一。进行中榜单只累计已经核验的贡献。

排名只按荣誉累计降序。相同总分为相同竞赛名次：rank=1+总分严格高于该人的人数。SQL窗口排序仅放总分；UID只放外层展示排序，不能放入RANK的胜负排序。分页稳定展示不改变同分名次。兑换、退款、网络快慢和核分顺序均不进入排名。

开放兑换时冻结榜单并记录rank_revision。冻结后禁止发放或使用补场授权；任何资格更正必须有操作者、原因、旧值、新值和修订号，不用恢复PLAYING绕过。

发现异常时按锁顺序从event阶段关口进入，再在同一参与者事务中设置review/claims_frozen，阻止新兑换及已有RESERVED订单产生新核销；冻结后涉及榜单修订的事务从event排他锁开始，不能持participant锁升级等待event锁。确认作废则追加全额冲正并更新当前槽贡献。未领取订单可按审计决定取消和原价退款。已领取的保留记录和待处理差额，不自动返库存，不自动承诺追回；负余额不直接改零。处理完后仅在资格明确、没有未决复核且余额不为负时解除冻结。冻结不妨碍授权人员只读查回已有CLAIMED记录。

核销与冻结/冲正按相同participant及订单锁顺序执行：先核销成功则留下已领取记录待人工处置；先冻结成功则后续核销拒绝。榜单更正与业务流水在同一事务形成可对账状态。

## 9. 礼品 订单和实物领取

### 9.1 配置与开放

主办方必须填写真实礼品名称、积分价格、库存、限领及claim_closes_at，实际领取截止应在界面公开。claim_closes_at缺失、格式非法或已到期时不能从DRAINING开放兑换。

首次开放后领取截止可以由主办方有审计地延长；不能悄悄缩短已公布截止影响已有订单。是否结束新兑换由REDEEMING→CLOSED决定，结束不改变既有订单已公布的领取截止。到领取截止后新兑换和核销均不可继续；允许完成取消退款等收尾。

### 9.2 下单

下单先认证归属、比对业务摘要并查询已有幂等订单；已存在则查回当前订单，不因后来CLOSED、过期或资格冻结而创建失败替代记录。只有新订单要求phase=REDEEMING、当前时刻<claim_closes_at、资格有效且未冻结、余额足够、库存可用，并且当前RESERVED+CLAIMED数量<1。按统一锁顺序串行化同人的资格/名额检查，锁内再次查幂等记录，不能只依靠按钮禁用。

同一事务创建RESERVED订单、记录价格快照、追加兑换扣分、可用库存减1和预留加1。失败全部回滚。订单保存随机核销凭证及必要显示信息；凭证不包含登录秘密。停用礼品只关闭新兑换，不能删除已建订单。

### 9.3 核销

核销员查询并核对必要身份后提交核销请求。服务端先认证核销权限、确认订单属于授权event、检查原业务摘要及当前订单：已CLAIMED时直接返回原claimed_at、核销员和“已领取”；已CANCELLED时返回已取消且不可领取。此类只读查回不再检查后来发生的资格冻结、领取截止或活动结束，也不重写状态。

只有RESERVED才进入首次核销事务；按统一顺序锁齐后再次读取当前订单，若已被其他操作变为CLAIMED/CANCELLED则返回该终态，不继续新副作用。仍为RESERVED时才检查参与者没有冻结/未决资格问题、当前时刻严格早于claim_closes_at，且阶段为REDEEMING或CLOSED。

事务将RESERVED改为CLAIMED、预留减1、已领取加1并保存claimed_at及核销员，不再次扣分。重复请求返回原核销记录和“已领取”，不重新产生一个领物动作。

现场操作顺序为“扫描查询→服务端核销成功→交付实物”。响应丢失须按原订单查询实际状态和核销记录；确认未核销才重试原请求，已核销则不能再次发物。只有一个纸质应急登记点的既有规则仍适用，不能各台独立脱机放行。

### 9.4 取消与到期

取消同样先认证归属并查已有业务/当前终态：已CANCELLED返回原取消结果，已CLAIMED明确返回不可取消且不退款。只有RESERVED才执行首次取消；用户可取消自己的订单，工作人员可按权限处理复核取消。CLOSED仍允许既有订单取消。默认在当前时刻>=claim_closes_at自动取消未领取订单；接口发现到期但任务尚未执行，也调用同一取消事务，不能继续核销。

取消/到期取消只允许RESERVED→CANCELLED，写明reason与时间；追加一次原成交价退款、预留减1、可用加1，释放一件名额。CLAIMED不可通过普通取消回退。取消、到期任务、核销三者争用相同状态条件，只能有一个终态。

总库存=可用+预留+已领取；所有分量非负。总量下调不得低于预留+已领取。已领取的异常后续处理不靠直接加库存或删订单完成。

## 10. 主办方操作关口

允许主路径：CHECK_IN→PLAYING→DRAINING→REDEEMING→CLOSED。首次开放前通过配置、资源、规则及06真人验收；正式挑战默认准入窗口20分钟，允许预先配置。

PLAYING到期由服务端关闭普通准入并推进DRAINING，客户端是否在线不影响。主办方可提前关闭；尚在PLAYING时可审计延长窗口，已DRAINING不借延长对全员重新开放。暂停开关不自动顺延任何截止。普通练习入口仅在CHECK_IN/PLAYING且开关允许时开放，暂停后不再新开练习；练习不进入正式局、槽位或积分记录。

PLAYING或DRAINING均可发限定名单、指定原槽和独立准入截止的故障补场；已在PLAYING发放的授权可跨普通截止在DRAINING使用。没有任务/在途也不能忽略仍有效的未用补场授权；主办方须等到期或明确取消并留痕后才封榜。

封榜开放兑换严格执行第6.4节；不能在尚有待复核或入口受理时强行略过检查。冻结后成绩更正走第8节，不重开挑战。CLOSED是正式活动阶段终态，保留既有订单在领取截止前的领取与取消能力，不产生新机会、新订单或新排名赛。

控制台分别显示：预约中、运行中、待上传、入口受理中、待核验、待复核、有效未用补场、预留礼品、已领取、到期未处理数。故障处理以实际对象为单位，不通过直接改余额或“给所有人加一次”代替原槽处理。

## 11. 运行 资产与容量门槛

正式start之前的资源预检确认必需图集成功解码、所需动画/帧键存在、模拟器与版本匹配、缓存可写；可选音效不影响静音开局。临时资产可以用于开发，但遵循与正式资产相同的manifest和锚点接口。四张原型不充当动画图集或碰撞数据。

按游戏加载并记录总纹理解码量、峰值内存及十轮切换后的变化；角色、阴影、场景、UI和碰撞独立。更换图片不改变模拟尺寸和难度。前端构建和资产路径带版本，在途局不被热替换删除所需资源。

初始混合负载按300名单、150同时游玩、100份终局5秒内到达，并叠加start和状态轮询。记录start、finish受理、查询、核分完成各自延迟分布、错误率、线程/连接池、队列峰值与最慢任务。核验P95目标5秒；此为待测目标，不能写成已测承诺。

至少分别记录自动化浏览器、移动视口模拟、实际手机微信及现场网络结果。界面帧率与逻辑时间分离；低帧不能多得操作时间。资源、CPU与数据库压力不足以满足现场规模时，先修复或调整部署/准入方案，不暗改玩法45秒、提交期限或得分。

正常启停、API异常重启、数据库恢复、任务租约恢复、领取响应丢失和期限到期都需有实际运行步骤。不得自动公网发布、购买服务或填入正式人员凭据；本地可运行不等于现场上线验收。
